BISTA HR · Backend Specification

Job Grades, Notches & the Job Title Cascade

Data model, relationships, validation rules and API contract for grade notches and the department → job title → grade/notch/benefits resolution used across People & Culture workflows.

Audience · Backend / API team Modules · Core HR, Payroll, People & Culture Status · Spec for implementation

1. Summary

Two additions to the existing Core HR model:

  1. Notches belong to a Job Grade. A grade owns an ordered band of notches — plain sequential integers starting at 1. Admins add a notch (appends the next number) or remove one (always confirmed); the remaining notches re-sequence so the band is always 1…N with no gaps.
  2. Job Titles resolve compensation. Every job title belongs to an organization and a department and carries a job grade + default notch. In People & Culture forms (Promotions first), selecting a department filters the available job titles; selecting a job title auto-resolves its grade, notch and the benefits (salary + allowances) for that grade/notch — no manual grade/notch entry.

2. Entity relationships

Organization→ Department→ Job Title→ Job Grade→ Notch→ Benefits (salary + allowances)
  • An Organization has many Departments.
  • A Department has many Job Titles. A Job Title belongs to exactly one Department (and, transitively, one Organization).
  • A Job Grade has many Notches (ordered, 1…N). A Notch belongs to exactly one Grade.
  • A Job Title references one Job Grade and one default Notch within that grade.
  • Benefits (base salary + allowances) are a function of (jobGradeId, notch) — owned by Payroll, not stored on the title.

Notch rules

1234 +
  • Notches are plain integers starting at 1, contiguous, no gaps — the band is always 1…N.
  • Add appends the next integer (N+1). No separate label/value — the number is the notch.
  • Remove is allowed but must always be confirmed by the user before it is applied. After removal the band re-sequences to 1…N-1 (the UI renders a confirm dialog; the API receives the final band).
  • Recommended guard: a grade should keep at least 1 notch. Reject removal that would empty the band, or that targets a notch currently assigned to an employee/job title (see “Referential safety”).
  • Persist either a single notchCount integer or an explicit ordered array — both are equivalent since notches are sequential. The array form is preferred if notches may later carry per-notch attributes (e.g. step value).
Referential safety. Before removing a notch, check it is not referenced by an active job title default notch or an employee’s current notch. If it is, block the removal (or require reassignment) and return a 409 Conflict with the blocking references.

5. The cascade (People & Culture forms)

Used on the Promotion form (and any P&C form that assigns a new job title). The three steps:

  1. Select Department → the Job Title field is filtered to titles where title.departmentId = department.id. Job Title is disabled until a department is chosen; changing department clears the title/grade/notch.
  2. Select Job Title → the system resolves jobGradeId + defaultNotch from the title and displays them as read-only (the user does not pick grade/notch manually).
  3. Benefits auto-fill → with (jobGradeId, notch) known, Payroll returns the base salary and allowances, shown read-only as “Benefits & Allowances”.

6. API contract

Job Grades

POST/api/job-grades
// create — notches default to [1,2,3] when omitted
{
  "name": "Grade 2",
  "code": "G2",
  "level": 2,
  "notchCount": 4,            // or "notches": [1,2,3,4]
  "description": "Standard professional grade.",
  "isActive": true
}
PUT/api/job-grades/{id}

Send the full resulting band (notchCount or the re-sequenced array). Removals are confirmed client-side; the server validates referential safety and re-sequences/persists.

GET/api/job-grades/{id}/notches
{ "jobGradeId": "…", "notches": [1, 2, 3, 4] }

Cascade lookups

GET/api/job-titles?departmentId={id}&active=true
[
  { "id": "jt_01", "name": "Finance Analyst", "jobGradeId": "g2", "defaultNotch": 1 },
  { "id": "jt_02", "name": "Accountant",      "jobGradeId": "g2", "defaultNotch": 2 }
]
GET/api/job-titles/{id}/resolution
// one call that returns grade + notch + benefits for a title
{
  "jobTitleId": "jt_01",
  "department": { "id": "d_fin", "name": "Finance" },
  "jobGrade":  { "id": "g2", "name": "Grade 2" },
  "notch": 1,
  "benefits": {
    "baseSalary": "GHS 7,000.00",
    "allowances": [
      { "label": "Transport Allowance", "value": "GHS 700.00" },
      { "label": "Housing Allowance",  "value": "GHS 1,050.00" }
    ]
  }
}
GET/api/payroll/benefits?jobGradeId={id}&notch={n}

Payroll-owned. Returns base salary + allowances for a grade/notch. The form may call this directly or rely on /job-titles/{id}/resolution which embeds it.

7. Validation & business rules

  • Notch values are integers ≥ 1, contiguous from 1, unique within a grade.
  • A job title’s defaultNotch must be ≤ its grade’s notch count.
  • Removing a notch requires explicit user confirmation (UI) and a server-side referential check (API).
  • When a grade’s notch count is reduced below a notch used by a title/employee, block or require reassignment.
  • A job title must reference a department within the same organization (tenant).
  • The cascade never lets the user type grade/notch — they are derived; the request submitted by the form carries the resolved jobGradeId + notch for audit.
